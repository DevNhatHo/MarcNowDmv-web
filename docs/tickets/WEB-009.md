# WEB-009 — MARC Pulse home experience

Status: DONE (2026-09-30)

## Goal

Offer a useful line overview within the existing contract.

## Why

This delivers the next bounded part of the local commuter milestone while preserving the data-trust and minimal-design rules.

## Dependencies

[WEB-005](WEB-005.md), [WEB-008](WEB-008.md)

## Scope

Create three line sections linking to filtered trains plus a small MARC advisory preview. Summarize reported official statuses only with clear service-date scope and completeness/unknown coverage; prefer plain explanatory text when counts would mislead.

## Out of Scope

Active/stationary counts, fabricated healthy line status, N+1 movement reads and backend aggregation.

## Expected Files

app/page.tsx, Pulse presentation components/helpers, home tests.

## Implementation Notes

Whole-day list is not running-now evidence. Never call a line Normal service because delays are absent. Partial pages cannot produce total counts. Keep the overview useful with line links and clear unavailable coverage rather than inventing confidence.

## Acceptance Criteria

Home answers what is known and what is unavailable; line links preserve date; advisories remain contextual; no KPI-card wall or unsupported operational totals.

## Tests Required

## Implementation decisions

**Everything is derived from one bounded read.** The screen fetches the train list once at
the maximum page size, plus the route catalog and a small alerts page — three requests, no
cursor follow and no per-train detail. A test asserts exactly three requests and zero
detail or `after=` calls.

**Absent evidence is never a healthy line.** A line with no current reports reads "N
scheduled. The operator is not currently reporting status for any of them." A test asserts
the words "on time", "normal", "good" and "running well" cannot appear for such a line.

**No active or stationary count is produced.** The backend defines no current-running
semantics (BACKEND-UI-02), so any such number would be this service's invention. The screen
says so in as many words: these figures "do not say how many trains are running now, which
this service cannot determine."

**Coverage is always stated, including what is missing.** Every summary names how many
trains it is based on and the service date, and says explicitly when more are scheduled than
were loaded.

**The advisory preview follows the alerts screen's rule**: an empty preview claims no
advisories only when the alert feed is healthy.

## Outcome

Added `lib/presentation/pulse.ts` and `components/PulseScreen.tsx` with its CSS module, and
replaced the last placeholder at `/`. Every route in the application is now a real screen.

Checks actually executed: `npm test` (**10 files, 155 tests**, 0 failures), `npm run lint`
(zero warnings), `npm run typecheck`, `npm run build` and `npx playwright test`.

Rendered verification against the live backend recorded the exact request list —
`trains?limit=200`, `routes?limit=200`, `alerts?limit=20`, and nothing else — with 0 px
horizontal overflow and no page errors at both viewports. Live copy read "Based on 96
scheduled trains for Wed, 30 Sept 2026, the whole service date" with all three lines
reporting that the operator is not currently reporting status. Each line link carried both
filters and landed on that filtered list.

Two copy defects were found by looking. "Received Reported just now" prefixed a phrase that
already begins with a verb, the same class of defect as WEB-005's "Reported not reported".
And "1 more retained advisory **are** not shown here" pluralised the noun but not the verb.
Both are fixed with regression tests.

## Limitations

The retained database reports no current status for any train, so **the partly-reported and
disrupted-line wordings were never exercised against live data**; they rest on unit tests
over constructed trains. The coverage sentence read "the whole service date" because 96
trains fit in one page, so the partial-view wording is likewise unit-tested but not captured
live. Chrome only; not a full accessibility audit.

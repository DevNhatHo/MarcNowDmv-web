## Implementation decisions

**A dwell is rendered only while the state is STATIONARY.** An UNKNOWN movement can still
carry the `stationarySeconds` it once observed; showing that would claim the train is still
stopped when tracking has actually been lost. `displayableStationarySeconds` owns that rule
in one place rather than leaving it to each call site.

**Each calculated object is read independently**, exactly as the backend evaluates them. A
stale or missing position reports movement unavailable while the delay trend, built from
official Trip Updates, is still reported. The two are never combined into one claim.

**Every calculated value is introduced by "MARC Now ·"** and the official block keeps
"Official MTA". The calculated blocks sit one step below the official status in the
hierarchy and never override it — which the synthetic captures demonstrate by leaving a
retained UNKNOWN status in place beside a fresh calculation.

**No replacement is ever invented.** A stop the operator reported skipped is said to be
reported skipped and the identified call stays as it is; PASSED_FINAL offers no substitute.
Choosing the following call would be manufacturing official information.

**A distance is worded only when the backend said it is in metres.** GTFS does not define
the unit of a source shape distance, so a different `units` value withholds the number
rather than relabelling it.

**Movement wording is purely physical.** "Moving" never implies punctuality, and
"Appears stationary" is explicitly not an official service status and offers no cause.

**Raw reasons, thresholds, windows and tolerances live only in the Data status disclosure**,
which stays closed. A test asserts that vocabulary such as `source_stale` never appears in
the commuter-facing part of the page.

## Outcome

Added `lib/presentation/movement.ts` and `components/Calculated.tsx` (`MovementStatus`,
`NextStopStatus`, `DelayTrend`) with its CSS module, and placed them in the detail hierarchy
the design wireframe specifies: official status, then movement with location, then next
stop, then delay trend, then stop times and diagnostics. A train whose response carries no
`calculated` group reads "Movement data isn't available for this train yet." Route progress
is parsed and surfaced in diagnostics only; without geometry there is nothing useful to
draw, and BACKEND-UI-03 gates that.

Checks actually executed: `npm test` (**8 files, 128 tests**, 0 failures), `npm run lint`
(zero warnings), `npm run typecheck`, `npm run build` and `npx playwright test` (**12 tests,
6 per viewport**).

Rendered verification covered the real retained screen plus six clearly labelled synthetic
scenarios rendered in the real UI by intercepting the detail response. The two rules most
easily got wrong are visible in the captures: a `stationarySeconds: 900` carried on an
UNKNOWN movement produced **no duration anywhere on the page**, and a stale position
produced "Movement unavailable" beside a live "Official delay improving". Horizontal
overflow was 0 px at both viewports with no page errors.

One defect was found by looking. The trend's basis delay restated the delay already shown in
the official block whenever the two agreed, which DESIGN.md forbids; the basis is now named
only when it differs, and all six synthetic captures show the figure exactly once.

## Limitations

**No fresh MOVING, STATIONARY, MEASURED or non-UNKNOWN trend has ever been observed from the
real backend.** Every fresh branch rests on fixtures and on screenshots of synthetic data in
the real UI, all labelled SYNTHETIC in the fixture file, in every export name and in the
review record. The only live captures show every calculation UNKNOWN.

Route progress has no commuter-facing presentation, by decision rather than omission.
Chrome only; not a full accessibility audit.

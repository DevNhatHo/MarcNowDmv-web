# WEB-005 — Service-date train list and train detail

## Goal

Help commuters choose a train without inventing active-service semantics, and make that
train's official status and schedule understandable at a glance.

## Why

This delivers the next bounded part of the local commuter milestone while preserving the
data-trust and minimal-design rules. It is also the first screen to consume the WEB-003
client, so it carries the real browser check of that boundary, which WEB-003 could not
perform because it added no UI.

## Implementation Notes

The list is a service-day schedule including completed trains. Use the verbatim tripId
fallback; no invented train numbers or headsigns. The default date respects the feed
timezone, `YYYYMMDD` is retained at the API boundary, and mixed-version catalog joins are
avoided.

A list continuation requires the `serviceDate` and `version` the cursor came from; the
client already refuses a cursor without them. Original-version names require matching
catalogs and otherwise fall back to identifiers. Do not present raw coordinates as being
near a named place. The envelope's `nextStop` and `nextUpdate` are pagination cursors, not
commuter next-stop information. Source diagnostics stay secondary.

`scheduleRelationship` is a nullable **numeric** GTFS-RT enum, at both trip and stop level.
This ticket owns mapping those numbers to labels, including the per-stop skipped case, and
records the mapping in DESIGN.md's status language table. An unrecognized number takes a
neutral unavailable label and is never guessed at.

## Acceptance Criteria

Filters survive navigation; partial pages are identified; UNKNOWN or stale official data
never reads as On time; zero delay differs visibly from null delay; empty copy says there
are no scheduled trains for the selected date and filter.

Official and scheduled values remain separately labeled; stale coordinates read as last
reported; null or unavailable detail is still useful; the back link preserves filters; and
no arrival time is derived in the browser.

Every list row links to a detail route that exists, and opening one returns that train.

## Implementation decisions

**Rows are ordered by scheduled departure.** The backend paginates by run identity, so its
order is not chronological; live rows arrived 19:45, 15:40, 06:12, 17:20. Sorting is
presentation over published scheduled times and infers nothing, but a later page can insert
rows above existing ones, so the partial notice says that explicitly rather than letting the
order look complete.

**The top-level `status` is the only current claim.** A retained `official.status` is shown
separately, phrased as what the operator *last published* and marked no longer current. A
row shows a delay only where one was published or the evidence is fresh, so a stale row is
not padded with a meaningless zero.

**Catalog names are joined only when schedule versions match**, for both line names and stop
names. A retained train from an older version keeps its identifiers rather than borrowing a
name that may since have moved.

**`describeReport` owns the absent case.** Concatenating a prefix onto `describeAge`
produced "Reported not reported" in the live list, so the absent case is now a whole phrase
rather than a fragment a caller can mis-assemble.

**One request per resource, with explicit refresh only.** `useResource` derives `loading`
by comparing the settled result against the request being asked for, so there is no
cascading render; a superseded response is discarded, a previous result for the *same* key
stays visible during a refresh, and a result for a *different* key is withheld. Ages render
against the clock captured when the response arrived, so no label ticks on its own.
Automatic polling remains WEB-010's.

**`scheduleRelationship` numbers are mapped, never guessed.** Documented trip and stop values
get labels; anything else reads "Reported status unavailable". The mapping is recorded in
DESIGN.md.

## Outcome

Added `lib/presentation/status.ts` and `time.ts`, `components/useResource.ts`,
`Feedback`, `TrainRow`, `TrainListScreen` and `TrainDetailScreen` with their CSS modules,
and wired `app/trains/page.tsx` and `app/trains/[id]/page.tsx`. The `/trains` placeholder is
gone; `/` and `/alerts` remain placeholders owned by WEB-009 and WEB-008.

Checks actually executed: `npm test` (**7 files, 107 tests**, 0 failures), `npm run lint`
(zero warnings), `npm run typecheck`, `npm run build` (both routes registered) and
`npx playwright test` (**12 tests, 6 per viewport**).

Manual verification ran against the real local backend reading retained `marc_208_live`,
with no ingestion and no schema change. The list returned 50 rows and "Load more" completed
the service date at **96 trains, ordered 04:50 → 20:05, with no duplicate identifiers**. A
row click opened that train's detail; the back link restored `?serviceDate=20260930`. A date
with no service rendered "No scheduled trains for Wed, 1 Jan 2020", and an unknown
identifier rendered "That train isn't available". Every live row read "Realtime status
unavailable · No report received" — correct for retained evidence, and nothing read "On
time". Horizontal overflow was 0 px and the smallest interactive target 44 px at both
viewports.

**The WEB-003 browser check is now discharged.** Both screens drove the typed client from a
real browser through `/api/backend/...` on the frontend origin, with **no CORS error** and
no page or console error beyond the two deliberate 404 probes.

Three defects were found by looking rather than by tests, all with every automated check
passing: rows read "Reported not reported"; the list arrived in backend rather than
chronological order; and detail showed the raw route id `11706` where the list showed
`CAMDEN - WASHINGTON`. All three are fixed, and the first has a regression test naming the
original wording.

## Limitations

The retained database holds no fresh realtime evidence, so **no live ON_TIME, delayed,
cancelled or fresh-position row was observed**. Those branches rest on unit tests over
captured and clearly synthetic fixtures, not on a screenshot. The loading state is captured
only incidentally, because the local backend answers in well under a second. Chrome only;
not a full accessibility audit.

Detail loads up to 200 scheduled stops and official updates in one request and says when
more exist, but does not yet page through `afterStop`/`afterUpdate`; no MARC trip in the
retained schedule approaches that bound. The client and contract support both cursors and
they are covered by WEB-003's tests.

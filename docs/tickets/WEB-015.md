# WEB-015 — Verify the app against live MARC service

Status: NOT_STARTED

## Goal

Replace the synthetic evidence behind the realtime presentations with observations of real
MARC service, and correct any record that overstates or understates what has been seen.

## Why

Most of this app was built against a retained snapshot of a completed service date, in which
every calculation reads UNKNOWN. The moving, stationary, measured-progress, identified-next-
stop and delay-trend presentations therefore rest on fixtures that were invented, clearly
labelled SYNTHETIC, and honestly recorded as never observed.

A first live ingest on 2026-09-30 at 22:23 EDT showed that is no longer necessary: two
ingests 35 seconds apart produced **MOVING**, **MEASURED** route progress, an **IDENTIFIED**
next stop and a **STABLE** delay trend from the real feed. Only two trains were reporting at
that hour, so the states were confirmed but not exercised at scale, and one real
inconsistency surfaced immediately (see [WEB-013](WEB-013.md)).

A verification pass at rush hour is now the cheapest way to raise confidence across several
finished tickets at once.

## Dependencies

[WEB-012](WEB-012.md).

## Scope

Run the stack against live feeds during a weekday peak with `cmd/ingest` polling, and record
what the app actually shows: movement states, route progress, next stop, delay trend,
position freshness transitions, the Pulse line summaries with real reported coverage, and
alert freshness against a current feed. Capture rendered evidence at both viewports. Update
the review records and ticket limitation sections that currently say a state has never been
observed, and open tickets for anything the live data exposes.

## Out of Scope

New features, map work, backend changes, feed ingestion into any database a reviewer depends
on without saying so, and reworking presentations that prove correct. Fixing newly found
defects beyond trivial copy is **out of scope**: record them as tickets so each is reviewed
on its own.

## Expected Files

docs/reviews/WEB-015/, docs/visual-review.md, docs/CURRENT_STATE.md, the limitation sections
of WEB-007, WEB-009 and WEB-010, new ticket files for anything found.

## Implementation Notes

The ingester is **one-shot**; nothing polls on its own. A loop is required:

```
go build -o /tmp/marc-ingest ./cmd/ingest
while true; do DATABASE_URL='…' /tmp/marc-ingest; sleep 30; done
```

Thirty seconds matches the frontend's trains cadence. Point it at the same database the API
serves, and **say in the record which database was written to**: ingesting changes the data
other reviews were captured against, so the choice between the retained review database and
a fresh one is a decision to state, not a detail to omit.

Weekday peaks are roughly 05:00–09:00 and 15:00–19:00 Eastern. Vehicle Positions payload size
is the quickest signal of whether trains are reporting: a few hundred bytes is effectively
empty, kilobytes means live GPS.

A stationary interval needs repeated nearby positions within the backend's own thresholds, so
STATIONARY is most likely to appear at a station dwell rather than on demand. If a state does
not occur, record that it did not; do not reconstruct it and present it as observed.

## Acceptance Criteria

Live observations of MOVING, route progress, next stop and delay trend are captured with
screenshots and recorded with their timestamp, service date and database. Every ticket or
review that currently claims a state has never been observed is either corrected or confirmed
still true. Any state that still could not be observed is named explicitly. Synthetic
fixtures remain in the test suite and remain labelled; nothing is deleted merely because a
live equivalent now exists.

## Tests Required

No new unit tests are required by this ticket unless a defect is found. Run all established
checks, including `npm run e2e` against the live backend, and confirm the integration suite
still passes with fresh data rather than retained data. Report the counts actually executed.

## Manual Verification

This ticket is manual verification. Observe at a real peak, at both viewports, and read the
screens as a commuter would rather than only asserting fields.

## Design Verification

Inspect rendered 360×800 mobile and 1280×900 desktop with live data against
[DESIGN.md](../DESIGN.md), including a moving train, a stale-position train and the Pulse
summary with genuine reported coverage. Capture screenshots with the WEB-004 tooling under
`docs/reviews/WEB-015/`; label every capture with its observation time. Missing screenshots
are an incomplete gate, not a pass. Automated tests alone do not satisfy this gate.

## Definition of Done

Live evidence is captured and recorded with its exact conditions; overstated or outdated
limitation sections are corrected; anything newly found has its own ticket. Review the diff
and update the ticket index, CURRENT_STATE.md and docs/visual-review.md. One completed-ticket
commit with a WEB-015 subject; preserve unrelated work. If service cannot be observed, record
why and leave IN_PROGRESS rather than making a completion commit.

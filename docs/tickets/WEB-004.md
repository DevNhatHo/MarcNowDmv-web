## Implementation decisions

**The brand is a link, not a heading.** Each page keeps the single `h1` that names what it
answers, so the heading outline describes the page rather than repeating the service name.
The document title is assembled by a metadata template instead.

**Only the navigation is a Client Component.** It is the one part that needs the current
path, so `AppShell`, the pages and the placeholders stay Server Components.

**The current destination is carried by three signals together** — colour, weight and a
persistent underline — so it survives grayscale and is announced through `aria-current`
rather than being visual only. A nested route belongs to its section, so train detail will
keep Trains current, while the home destination matches exactly.

**Placeholders are deliberately plain and contain no figures.** A placeholder that
resembled data would be read as data, and unavailable information must never look like a
healthy answer. Each one says explicitly that an empty screen is not an operational claim,
and a test asserts the Pulse placeholder contains no digit at all.

**Browser review tooling is Playwright driving the installed system Chrome** through the
`chrome` channel, so no browser binary is downloaded into the repository or a cache. The
two projects are exactly the viewports the design gate requires. Vitest owns
`tests/**/*.test.ts(x)` and Playwright owns `tests/e2e/**/*.spec.ts`, so neither runner
collects the other's files.

## Outcome

Added `components/AppShell`, `SiteNavigation` and `RoutePlaceholder` with their CSS
modules, rewrote `app/layout.tsx` to wrap every page in the shell, and added `/trains` and
`/alerts` beside a rewritten `/`. Removed the starter's `app/page.module.css` and its
duplicated affiliation disclosure, which the footer now carries verbatim. Added
`playwright.config.ts`, `tests/e2e/shell.spec.ts` and an `npm run e2e` script, and pinned
`@playwright/test` to an exact version to match the repository's existing convention.

Acceptance criteria evidenced: all three destinations navigate and mark themselves current
in a real browser; the skip link is the first tab stop, shows a 3 px focus ring and moves
focus to the main landmark; the footer string matches the required wording character for
character and appears exactly once per page; and the shell reads naturally at 360×800 and
1280×900 with zero horizontal overflow at both.

Checks actually executed: `npm test` (**5 files, 74 tests**, 0 failures), `npm run lint`
(zero warnings), `npm run typecheck`, `npm run build` (`/`, `/trains`, `/alerts` static,
`/api/backend/[...path]` dynamic) and `npx playwright test` (**12 tests, 6 per viewport,
all passing**).

Two defects were found and fixed during the work. The root page rendered a bare `Pulse`
title while the other two rendered the full template, because Next's `title.template`
applies to **child** segments only and the home page shares the root layout's segment; it
now sets its title absolutely, with a comment recording why. Separately, and only visible
by looking, navigation labels broke **mid-word** at 200% zoom on a 360 px viewport —
"Puls/e", "Train/s", "Alert/s" — because WEB-002's global `overflow-wrap: anywhere`, which
exists so a long opaque identifier cannot overflow, is wrong for a short label. Every
automated check passed while this was broken. The navigation and brand now set
`overflow-wrap: normal` and the list wraps between items.

## Rendered verification

Full evidence, measurements and the design checklist are in
[the review record](../reviews/WEB-004/README.md), with fourteen screenshots. Measured from
the live DOM at both viewports: 0 px horizontal overflow, 44 px navigation targets, one
`h1` per page, 960 px capped content width on desktop, a 3 px skip-link focus ring, and
`--motion-duration` resolving to 0s under reduced motion. Grayscale captures confirm the
current destination does not depend on colour, and a synthetic long-identifier probe
confirms an opaque token still cannot force horizontal scroll.

## Limitations

Loading, error and real-data states are **not applicable** to this ticket: the shell
performs no fetch and no screen consumes the WEB-003 client yet. Those states belong to
WEB-005, WEB-008 and WEB-009. The rendered review used Chrome only and is not a full
accessibility audit or a screen-reader certification.

The real browser check of the WEB-003 client, which WEB-003 recorded as owed, is still
owed: this ticket added no screen that loads data, so there was nothing to exercise it
through. It belongs to WEB-005, the first screen to call the client.

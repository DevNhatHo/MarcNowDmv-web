## Implementation decisions

**Structure is strict, vocabulary is not.** A missing object, a wrong primitive type or a
non-finite number fails parsing with the exact path that disagreed, because a
structurally wrong response cannot be trusted at all. An unrecognized enum value always
parses and is preserved verbatim, because a new backend state must degrade to a neutral
unknown in presentation rather than break a screen. `isKnown` reports whether a value has
an explicit frontend label, so an unknown state can never be styled as healthy.

**Wire types were derived from the handler DTOs, not from prose.** Reading
`internal/httpapi/trains.go` and `catalog.go` corrected six field types the captures could
not reveal, because the sampled values happened to be present or integral; the table is in
[API_CONTRACT.md](../API_CONTRACT.md). Most consequential:
`scheduleRelationship` is a nullable **number**, and `officialStopUpdates[].stopId` and
`.resolvedSequence` are **nullable**, so an unresolved update must never be drawn on the
schedule timeline.

**Cursor rules were verified in the query parsers.** A train list cursor requires both
`serviceDate` and `version` and the backend additionally rejects a token whose embedded
service date differs; an alert cursor requires both `snapshot` and `version`; train detail
accepts no `version` at all. The client refuses these combinations as a typed `usage`
failure, so a request certain to return 400 is never sent.

**Timestamps stay ISO strings and identifiers stay strings.** Nothing is converted to
`Date` or to a number at the boundary, so no observation id loses precision and no
timezone is silently assumed. Provenance groups are carried through unmerged, and no
parser derives, defaults or fills a value the backend did not send: a missing delay stays
null and never becomes zero.

**The proxy is a pass-through with an allowlist.** Upstream status, JSON body and
content type are preserved byte for byte. Only GET and HEAD are exported so every other
method gets 405 from the framework. Redirects are never followed (502
`upstream_redirect`), non-HTTP origins are refused, a timeout is 504 `upstream_timeout`, an
unreachable backend is 502 `upstream_unavailable`, client cancellation is 499
`request_cancelled`, and a path outside the allowlist is 404 without contacting the backend
at all. Failure envelopes reuse the backend's `{error:{code,message}}` shape so the client
has one parsing path, and no upstream body is echoed into an error.

**Continuation is bounded and never blends versions.** `collectPages` walks at most ten
pages, inspects the cursor *before* constructing the next request, rejects a page whose
schedule version or snapshot identity changed as `mixed_version`, and restarts exactly once
on a 409 before propagating. A walk stopped by the bound reports `complete: false`, so a
partial list cannot be presented as a complete total.

## Outcome

Added the wire contract (`lib/types/*`), guards and parsers (`lib/api/contract.ts`,
`parse.ts`), typed failures (`errors.ts`), the centralized client (`client.ts`), resource
modules for trains, alerts, catalogs and health, bounded continuation (`pagination.ts`),
the shared path allowlist (`paths.ts`), the proxy (`proxy.ts`) and its route handler
`app/api/backend/[...path]/route.ts`. No product UI was added and no existing page changed.

Acceptance criteria evidenced by tests: every captured response parses with provenance
groups separate and identifiers as strings; unknown enum values survive parsing and report
as not known; nulls, absent lists and a null `calculated` group parse as absence rather
than failure; invalid payloads fail with the disagreeing path; 400/404/409/5xx each carry
their backend code; a non-envelope error body is not echoed; abort and timeout are
distinguished; the route allowlist refuses undefined paths, traversal and multi-segment
identifiers without contacting the backend; encoded identifiers round-trip; both detail
cursors and the alert snapshot cursor are sent correctly; and a 409 restarts the walk once
while a second 409 propagates.

Two defects were found by the tests rather than by review. Resource readers threw usage
errors **synchronously**, so a caller would have needed both `try/catch` and `.catch`; they
are now `async` and always reject. More seriously, the first continuation walk called the
next-page function *before* checking the page bound, which issued a request it then
discarded and left an unawaited promise able to reject unhandled; the interface now
separates `cursor` from `after` so the bound is checked before any request is built.

Checks actually executed: `npm test` (**five files, 64 tests, 0 failures**), `npm run lint`
(zero warnings), `npm run typecheck`, `npm run build` (production build succeeded;
`/api/backend/[...path]` registered as a dynamic route).

Manual verification actually executed against the real local stack — backend `cmd/api` on
127.0.0.1:8080 reading the retained planning database `marc_208_live`, frontend `npm start`
on localhost:3000, no ingestion and no schema change:

- `/health`, `/api/v1/routes` and `/api/v1/stops?limit=5` returned **byte-identical** bodies
  through the proxy and directly from the backend. `/api/v1/trains` and `/api/v1/alerts`
  differed **only** in `evaluatedAt` (23–35 ms apart), which is the read clock; every other
  field compared equal.
- Detail returned 200 with `calculated` as a sibling of `data`; `?afterStop=1` and
  `?afterUpdate=1` returned 200 while the incorrect `?stopAfter=1` returned 400, confirming
  the cursor names in live traffic.
- `limit=bad` returned 400 and an unknown detail token returned 404, both preserved verbatim.
- `/api/v1/routes/not-a-route`, `/metrics` and `/api/v2/trains` returned 404 from the proxy
  with **zero** corresponding entries in the backend log, proving the allowlist refused them
  rather than forwarding them.
- POST, PUT, DELETE and PATCH each returned 405; HEAD `/health` returned 200 with no body;
  every proxy response carried `Cache-Control: no-store`.
- The backend returned **no** `Access-Control-Allow-*` header even when sent an
  `Origin: http://localhost:3000` request, while the proxy path is same-origin, so the
  browser never performs a cross-origin request and no backend CORS change is needed.
- A temporary live smoke test drove the typed client through the proxy and was deleted
  afterwards, because the permanent suite must stay deterministic. It parsed health,
  catalogs, list, detail, both detail cursors and alerts from today's live responses, and a
  bounded walk collected **96 trains over 2 pages with `complete: true` and no duplicate
  identifiers**. Every calculated state read UNKNOWN and position freshness UNAVAILABLE,
  which is correct for retained data from a completed service date; `nextStop.units` was
  `meters` while `routeProgress.sourceDistanceUnits` stayed `unknown`, so the two distance
  units are not conflated. An unknown token surfaced as a typed 404 failure.

## Limitations

No fresh MOVING, STATIONARY, MEASURED or non-UNKNOWN trend response was observed, because
the retained database holds no live service; those branches are covered by fixtures in
`tests/fixtures/synthetic.ts`, which are labelled SYNTHETIC in the file, in every export
name and in their comments, and are never described as observations.

No browser was driven. This ticket adds no UI that loads the client, so the same-origin
property was verified by HTTP instead: the backend sends no CORS headers, and the proxy
serves from the frontend origin. A real browser check belongs with the first screen that
consumes the client. Design verification is not applicable, as the ticket states.

`npm test` now also collects `tests/**/*.test.ts` alongside `.test.tsx`; the command itself
is unchanged.

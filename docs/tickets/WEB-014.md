# WEB-014 — Show the operator's scheduled destination

Status: NOT_STARTED

## Goal

Replace the opaque trip identifier with the destination the operator actually publishes,
wherever that destination can be established honestly.

## Why

Every screen currently identifies a train by its verbatim `tripId` — "Train548" — because the
contract review concluded no destination was exposed. WEB-MAP-1 found that conclusion wrong:
`GET /api/v1/departures` returns a scheduled `headsign` per trip at a stop, "UNION STATION"
in the captured response. A commuter chooses a train by where it goes, so this is the single
largest readability gain available without any backend change.

## Dependencies

[WEB-005](WEB-005.md).

## Scope

Read `/api/v1/departures` through the typed client, add its wire types and parser, and use
the scheduled `headsign` to label trains on the list, the detail screen and the Pulse
preview. Define and implement the fallback when no headsign can be established. Keep the
verbatim `tripId` visible wherever identity matters for support or diagnosis.

## Out of Scope

Inventing a direction, deriving a destination from stop sequence or shape order, parsing the
trip identifier for meaning, a per-train request fan-out, a new station or departures screen,
and any backend change.

## Implementation Notes

The endpoint is **stop-scoped**, and the screens are train-scoped: this mismatch is the whole
difficulty and must be solved by bounded reads, not by a request per train. One departures
read per line's origin stop, for the displayed service date, yields a `tripId → headsign` map
that covers that line's trains; the architecture's catalog cadence suits it, since it is
SCHEDULED data that changes only on activation.

The proxy allowlist must gain `/api/v1/departures`; it is currently refused, correctly,
because nothing used it.

Its service date is **`YYYY-MM-DD`**, not the `YYYYMMDD` every other endpoint takes. Sending
the wrong format returns 400. It also requires `stopId`, and accepts `from`/`to` service
seconds, `windowStart`/`windowEnd`, `after`, `limit`, `version` and `routeId`.

A headsign is SCHEDULED provenance. It describes where a train is booked to go, not where it
is going now, so it must not be rendered as realtime information or allowed to imply a
current claim. Join it only when schedule versions match, as line and stop names already do.
Where no headsign can be established, fall back to the `tripId` exactly as today — an unknown
destination is never guessed.

## Acceptance Criteria

A train whose headsign is known is identified by it, with the `tripId` still available; a
train whose headsign is unknown is unchanged from today. No screen issues a request per
train, and the bounded read count is asserted. Headsigns from a different schedule version
are not used. The `YYYY-MM-DD` format is sent correctly, and a wrong format cannot be
constructed by the client.

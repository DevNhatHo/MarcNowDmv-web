# WEB-011 — Responsive accessibility and design review

Status: DONE (2026-09-30)

## Goal

Finish a consistent, accessible commuter experience across all screens.

## Why

This delivers the next bounded part of the local commuter milestone while preserving the data-trust and minimal-design rules.

## Dependencies

[WEB-010](WEB-010.md)

## Scope

Perform the design checklist across Pulse/list/detail/alerts; fix spacing/wrapping, hierarchy, redundant containers, focus, semantic labels, contrast, touch targets, reduced motion and live announcements. Capture rendered review evidence.

## Out of Scope

New features, maps, dark mode, rebranding and backend modifications.

## Expected Files

Existing screen/component/CSS files as needed, tests/e2e/*, docs/visual-review.md, docs/DESIGN.md.

## Implementation Notes

Use real retained data plus explicit synthetic fresh/empty/error states. Review without color and at 200% zoom. Do not add decorative assets to cover information problems.

## Acceptance Criteria

Every screen has clear priority, mobile/desktop evidence and accessible keyboard flow; UNKNOWN/STALE/healthy differ in text; calculations remain distinct; no horizontal overflow or tiny controls; remaining limitations are explicit.

## Tests Required

Run all established checks and browser scenarios at 360×800/1280×900. Record contrast and manual screen-reader/keyboard observations; do not claim a full accessibility audit from an automated tool alone.

## Manual Verification

Review every screen and detail branch with design checklist; loading/empty/error/real data required. Capture screenshots where tooling allows and list exact evidence paths.

## Design Verification

Inspect rendered mobile and desktop views using [the design checklist](../DESIGN.md). Review hierarchy, spacing, wrapping, color-independent status and applicable loading/empty/error/real-data states. Capture screenshots with the Playwright tooling established in WEB-004 and record them under `docs/reviews/<ticket>/`; state explicitly which states are inapplicable and why. Missing screenshots are an incomplete gate, not a pass. Automated tests alone do not satisfy this gate.

## Outcome

Added an automated accessibility floor rather than a one-off inspection:
`tests/e2e/accessibility.spec.ts` runs axe (WCAG 2.0/2.1 A and AA) on every screen at both
viewports, plus the checks axe does not make — standalone control height, horizontal scroll,
list names, heading count, focus rings, reduced motion, and a failed refresh that retains its
content and announces politely. `@axe-core/playwright` and `axe-core` are pinned exactly, as
this repository's convention requires. The durable record is
[docs/visual-review.md](../visual-review.md).

Four classes of defect were found and fixed:

1. **Eleven standalone controls across four screens were under 44 px** — the skip link
   (40 px), brand (30 px), "See all MARC advisories" (22 px), "Read the operator's notice"
   (24 px) and "← Back to trains" (19 px). A `.standalone-link` utility gives them the full
   minimum height while links inside prose keep their natural size, per WCAG 2.5.5's inline
   exception.
2. **Form controls could focus without a ring**, so `input`, `select` and `textarea` now show
   it on plain `:focus` as well as `:focus-visible`.
3. **Eight lists in `main` were unnamed**, so a screen reader could not tell the trains list
   from an advisory's scope list or the diagnostics lists. All are named now.
4. **A failed refresh changed silently.** A visually hidden polite live region now announces
   the *state* only, never the timestamp: announcing the banner itself would read every tick
   aloud, which the architecture rules out.

After the fixes, all eight screen-and-viewport combinations report **0 axe violations, 0
undersized standalone controls, 0 unnamed lists, 0 px horizontal overflow and exactly one
`h1`**.

Checks actually executed: `npm test` (**11 files, 169 tests**), `npm run lint` (zero
warnings), `npm run typecheck`, `npm run build` and `npx playwright test` (**26 tests, 13 per
viewport**).

## Limitations

**This is not a certified accessibility audit**, and the documentation says so plainly. It is
an automated floor plus a rendered review in one browser: no screen reader was driven, no
other engine was tested, no user testing was done, and axe finds a minority of real barriers
by design.

One gap is documented rather than fixed: tabbing through `<input type="date">` crosses
Chrome's internal sub-fields, and one picker part inside the shadow DOM takes no page CSS.
Replacing the native control would trade a small native gap for a larger custom one.

The delayed, cancelled, moving and stationary presentations were reviewed against clearly
labelled synthetic fixtures, because the retained database never produces them.
